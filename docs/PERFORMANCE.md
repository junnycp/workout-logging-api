# Performance on 50,000+ entries per user (E6)

The brief asks that "endpoints must perform well with 50,000+ workout entries per user". This document gives the
dataset, the method, the results against targets that were set before measuring, and the known limits. Every
number here comes from a file in [`docs/perf/`](perf/), unless it is marked as coming from command output.
All of it can be reproduced with the commands below.

Measured 2026-10-09.

## 1. Reproduce

```bash
docker compose up -d --build                          # API + Postgres, migrations, catalog
export DATABASE_URL=postgresql://workouts:workouts@localhost:5432/workouts

# Main dataset (perf-single absent: a seed always replaces every profile user)
docker compose --profile perf run --rm seed-perf       # or: npm run seed:perf
docker compose restart postgres                       # empties shared_buffers
npm run perf:plans -- --label cold                    # docs/perf/plans/cold/
npm run perf:plans -- --label warm                    # docs/perf/plans/warm/
docker compose restart api
PERF_API_URL=http://localhost:3000 npm run perf:latency -- --label warm      # docs/perf/latency-warm.md

# Worst case, measured on its own
npm run seed:perf -- --include-optional
npm run perf:plans -- --label single --only S         # run twice; the second (warm) run is the one kept
PERF_API_URL=http://localhost:3000 npm run perf:latency -- --label single --only S
```

## 2. Dataset

The dataset is defined in `prisma/seed/perf-profile.json` and generated by `src/perf/perf-dataset.ts`:
- A seeded PRNG per user produces the same rows and ids on every machine. A unit test pins a SHA-256 of a
  generated user.
- Dates end at a fixed past anchor (2026-10-01), so they stay valid under D12.
- Derived columns come from `computeSetMetrics`, the same function the API uses.
- Set ids ascend with the set number, as the API's `uuidv7()` ids do.
- The seed ends with `VACUUM (ANALYZE)`. "Heap Fetches: 0" in the plans depends on that visibility map; in
  production, autovacuum's insert threshold (PostgreSQL 13+) sets it the same way.

| User | Entries | Sets (all / weighted) | Shape |
|------|--------:|------------------------|-------|
| `perf-heavy` | 50,000 | 225,395 in total | 3 years, 30 exercises with Zipf-like frequency, 3–6 sets per entry, progressive weights rounded to 2.5 kg / 5 lb, ~15 % lb entries, ~5 % bodyweight entries, 6 UTC offsets. The most-logged exercise, Bench Press, has 53,136 weighted sets |
| | | | Risky cases on purpose: Sumo Deadlift only in the first 180 days, Pull-Up bodyweight-only, Barbell Row plateau (174 sets at exactly 100 kg × 5), 30 entries at one instant |
| `perf-bg-001…050` | 2,000 each | ~9k each | same generator: a multi-user table, so planner statistics are realistic |
| `perf-single` (optional, measured separately) | 50,000 | 224,622 / 213,318 | one exercise only: the worst case for records |

| Main dataset (`docs/perf/plans/warm/summary.md`) | Rows | Heap | Indexes | Total |
|---|---:|---:|---:|---:|
| `workout_entries` | 150,011 | 27 MB | 62 MB | 89 MB |
| `workout_sets` | 675,236 | 178 MB | 282 MB (PR covering index 192 MB) | 460 MB |

The heaps include free space left by earlier re-seeds of the same database. Before any re-seed, the first full seed
(900k sets) had a 118 MB `workout_sets` heap (command output).

Seed time (command output): 98.5 s for the main dataset (150k entries, 675,222 sets) and 129.7 s with
`perf-single`. That is about 8.4–8.7k rows/s through batched `createMany`.

## 3. Method

- **Plans** (`npm run perf:plans`):
  - The real app runs in-process. Its `PrismaService` is replaced by a client on a dedicated pool whose sessions load `auto_explain` (`log_analyze`, `log_buffers`, `log_triggers`).
  - Each executed statement's plan comes back to the client as a NOTICE with its SQL and parameters. Nothing is re-run or rebuilt from logs.
  - Durations include EXPLAIN ANALYZE timing overhead, so they are upper bounds.
  - One call per scenario: the first request variant.
- **Latency** (`npm run perf:latency`):
  - `fetch` against the compose `api` container, a separate process with no EXPLAIN instrumentation.
  - 5 warm-up calls, then 100 sequential calls cycling through each scenario's request variants (users, cursors at depths 1k–49k, exercises, ranges). The max bulk is capped at 20 calls.
  - Every read checks its content (non-empty page, record present or absent as expected), so missing data fails the run instead of looking fast.
  - Two scenarios are also run in closed-loop batches of 20 parallel requests. Each batch waits for its slowest request, so these are not open-loop load tests.
  - Rows written by POST scenarios are deleted after each scenario. POST scenarios run last.
- **Cold vs warm.** "Cold" means right after `docker compose restart postgres`: **empty `shared_buffers` only**. The Docker VM's page cache was not dropped, so "cold" reads still come from VM memory. `Buffers read` is the machine-independent signal.
- **Environment.**
  - Apple M2 laptop, Colima VM with 2 vCPU / 2 GB RAM, PostgreSQL 16.15 (alpine image).
  - Default settings: `shared_buffers` 128 MB, `work_mem` 4 MB, 2 parallel workers per gather.
  - API: Node 24, pg pool at its default of 10 connections.

## 5. Findings

1. **History does not depend on depth or data volume.**
   - Every page is an index scan that stops after `limit + 1` rows. It runs either on
     `(user_id, performed_at DESC, id DESC)`, or once per matched exercise on
     `(user_id, exercise_id, performed_at DESC, id DESC)`.
   - In this run the planner served the deep-cursor page as a Bitmap Heap Scan on the same index; it reads 20 rows
     either way.
   - Filtered pages read ≤ 21 rows per matched exercise. That includes the exercise last logged two years ago
     (the M5 skew case) and the broad term `e` (51 × 12 rows).
2. **Records scale with the weighted sets of one (user, exercise), not with the user's total.**
   - Each metric is an Index Only Scan with 0 heap fetches over that slice of `workout_sets_pr_covering_idx`
     (D10). A top-N sort follows, and the scan returns the top 50.
   - Typical exercise (5,905 sets): 3.8 ms per metric query.
   - The most-logged exercise of a 50k-entry user (53k sets): ~30 ms per request with parallel workers, and up to
     61 ms per statement when the index pages are not in shared_buffers.
   - A one-month range reads only that month: < 1 ms.
3. **Known limit: one exercise logged 50k times.**
   - `perf-single` PRs take 92.4 ms p95: three parallel index-only scans of 213k index tuples, i.e. up to 6
     parallel workers on 2 vCPUs.
   - This is the case D10 accepted. The scale path is a per-(user, exercise) record summary maintained in the POST
     transaction (D6), which makes all-time records O(1).
   - Range queries and compare keep using this index; S2 compare has a p95 of 15.1 ms.
4. **Ties on the top value cost extra statements.**
   - When all 50 candidates tie on the top stored value, a second query fetches every tied set. That query has no
     LIMIT (`personal-records.repository.ts`). `findSets` then loads all of them for exact ranking.
   - Measured: P4 (174 ties, 10 statements) p95 7.6 ms; P5 (53 ties, 8 statements) p95 7.3 ms.
   - The cost grows with the number of identical sets. The plan-review spike measured 66,668 identical sets at
     73 ms + 412 ms (AI_WORKFLOW C23; that database was dropped). Reaching that needs tens of thousands of sets at
     exactly one weight.
   - Documented, not bounded. The fix if it matters is `ORDER BY reps DESC, performed_at, id LIMIT n` on the tied
     value.
5. **No row misestimate makes a plan worse, so no extended statistics (T1, D13).** The rule fixed before
   measuring: add statistics only if an estimate is off by ≥ 10× **and** that makes the plan worse.
   - Main dataset, warm (`plans/warm`): every candidate scan on `user_id = ? AND exercise_id = ?` is within 1.2×
     (P1: 22,035 estimated vs 17,712 actual per worker; P2: 6,106 vs 5,905).
   - Every ≥ 10× ratio in the committed plans:
     - The history scans (H1 49,299 vs 21; H8 49,299 vs 101; H3–H6 1,494 vs 11–21 per exercise). The estimate is
       the whole user slice; the scan stops at the LIMIT.
     - P6's three candidate scans (859 vs 0: the exercise has no weighted sets) and its bodyweight check (50 vs 1,
       a `LIMIT 1` stopping early).
     - P4's tie query (1 vs 174, an equality on one `weight_kg` value).
   - All of these stay Index (Only) Scans on the intended index, so the rule does not apply.
   - Observation: with `perf-single` in the table, the P1 estimate was 38,292 vs 17,712 (commit `46e7d62`, since
     replaced). That is the skew the approved plan separated `perf-single` to avoid.
6. **Concurrency is bounded by the connection pool and 2 vCPUs.**
   - The pool is not configured, so it uses pg's default of 10 connections. A records request runs its three
     candidate queries in parallel.
   - Batches of 20 records requests: p95 85.7 ms. Batches of 20 history requests: p95 62.4 ms.
   - Requests queue; none fails.
   - At scale: a configurable pool size, PgBouncer in transaction mode, and read replicas for history and records.
7. **Writes.**
   - One entry: p95 4.6 ms.
   - Max bulk (5,000 sets): p95 322 ms.
   - The instrumented plans pass shows 5 statements: 2 name lookups, 1 `INSERT` of entries and 2 `INSERT`s of sets
     (Prisma splits the sets at the bind-parameter limit: 2,730 + 2,270 rows). Together they take ≤ 81 ms, of which
     FK triggers are ≈ 49 ms.
   - The remaining ~200 ms was not profiled (validation, decimal.js metrics, serialization are candidates).
8. **Index usage** during the plans pass (`plans/warm/summary.md`): every index on `workout_entries` and
   `workout_sets` was used. Six indexes on small tables had 0 scans:
   - `idempotency_keys_pkey` and `idempotency_keys_created_at_idx`: no scenario sends an `Idempotency-Key`.
     `created_at` exists for a future cleanup job (T2).
   - `exercise_names_name_key_trgm_idx`: the catalog has ~150 names, so a Seq Scan is cheaper. The index matters
     if the catalog grows (T3).
   - `exercise_names_pkey`, `exercises_name_key`, `exercise_muscle_groups_pkey`: the lookups on these tiny tables
     are Seq Scans for the same reason.
   - Most `workout_entries_pkey` scans come from FK checks of the bulk POST and from deleting its rows.
9. **Write amplification is the price of D10.** The PR covering index (192 MB) is larger than the
   `workout_sets` heap. Each logged set writes three index entries on that table.

## 6. What would change at scale

| Pressure | Change |
|----------|--------|
| All-time records for exercises with very many sets (findings 2, 3) | `exercise_records` summary per (user, exercise, metric), updated in the POST transaction; ranges stay on the covering index |
| Many concurrent coaches (finding 6) | Pool size from config, PgBouncer, read replicas for GET endpoints, a statement timeout |
| `workout_sets` growth (hundreds of millions of rows) | Partition by `user_id` hash, or by time with partition pruning on `performed_at` |
| Very large tie groups (finding 4) | Bound the tie query |
| Bulk POST latency (finding 7) | Profile the application share first; then COPY, or return only ids instead of the full echo |
