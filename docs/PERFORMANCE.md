# Performance on 50,000+ entries per user (E6)

The brief asks that "endpoints must perform well with 50,000+ workout entries per user". This document has the
dataset, the method, the measured results against targets set before measuring, and the known limits. All of it
can be reproduced from the repository. Raw plans and generated reports are in [`docs/perf/`](perf/).

Measured 2026-10-09 on branch `m7`.

## 1. Reproduce

```bash
docker compose up -d --build                         # API + Postgres, migrations, catalog
docker compose --profile perf run --rm seed-perf \
  node dist/cli/seed-perf.js --include-optional      # dataset below, ~2 min, idempotent
export DATABASE_URL=postgresql://workouts:workouts@localhost:5432/workouts
docker compose restart postgres                      # empties shared_buffers
npm run perf:plans -- --label cold                   # docs/perf/plans/cold/
npm run perf:plans -- --label warm                   # docs/perf/plans/warm/
docker compose restart api
PERF_API_URL=http://localhost:3000 npm run perf:latency -- --label warm   # docs/perf/latency-warm.md
```

Without `--include-optional` the seed skips `perf-single`, and the `S*` scenarios are left out.

## 2. Dataset

The dataset is defined in `prisma/seed/perf-profile.json` and generated by `src/perf/perf-dataset.ts`:
- A seeded PRNG per user produces the same rows and the same ids on every run.
- Dates end at a fixed past anchor, 2026-10-01, so they stay valid under D12.
- Derived columns come from `computeSetMetrics`, the same function the API uses.

| User | Entries | Sets | Shape |
|------|--------:|-----:|-------|
| `perf-heavy` | 50,000 | 225,395 | 3 years, 30 exercises with Zipf-like frequency (Bench Press 53k sets, the rarest ~1.7k), 3–6 sets per entry, progressive weights rounded to 2.5 kg / 5 lb, ~15 % lb entries, ~5 % bodyweight entries, 6 UTC offsets |
| | | | Risky cases on purpose: Sumo Deadlift only in the first 180 days, Pull-Up bodyweight-only, Barbell Row plateau (174 sets tied at 100 kg × 5), 30 entries at one instant |
| `perf-bg-001…050` | 2,000 each | ~9k each | same generator; a multi-user table, so planner statistics are realistic |
| `perf-single` (optional) | 50,000 | ~213k | one exercise only: the worst case for records |
| **Total** | **200,000** | **899,844** | `workout_entries` 82 MB (20 MB heap, 62 MB indexes), `workout_sets` 404 MB (139 MB heap, 266 MB indexes, of which the PR covering index is 177 MB) |

Seeding time: 128 s for everything (about 8.6k rows/s through batched `createMany`), and 130 s to re-seed the
same users.

## 3. Method

- **Plans** (`npm run perf:plans`):
  - The real app runs in-process. Its `PrismaService` is replaced by a client on a dedicated pool whose sessions load `auto_explain` (`log_analyze`, `log_buffers`, `log_triggers`).
  - Every executed statement's plan returns to the client as a NOTICE with its SQL and parameters. Nothing is re-run, and nothing is rebuilt from logs.
  - Durations include EXPLAIN ANALYZE overhead, so they are upper bounds.
- **Latency** (`npm run perf:latency`):
  - `fetch` against the compose `api` container, a separate process, so the client does not share the server's event loop and no EXPLAIN instrumentation is active.
  - 5 warm-up calls, then 100 calls cycling through each scenario's variants (users, cursors at depths 1k–49k, exercises, ranges). The max bulk is capped at 20 calls.
  - Two scenarios also run with 20 requests in flight.
  - Rows written by POST scenarios are deleted after each scenario.
- **Cold vs warm.** "Cold" means right after `docker compose restart postgres`, i.e. **empty `shared_buffers` only**. The Docker VM's page cache was not dropped, so cold reads still come from VM memory. `Buffers read` is the machine-independent signal.
- **Environment.**
  - Apple M2 laptop, Colima VM with 2 vCPU / 2 GB RAM, PostgreSQL 16.15 (alpine image).
  - Default settings: `shared_buffers` 128 MB, `work_mem` 4 MB, 2 parallel workers per gather.
  - API: Node 24, pg pool at its default of 10 connections.

## 5. Findings

1. **History does not depend on depth or data volume.** Every page is an Index Scan on
   `(user_id, performed_at DESC, id DESC)`, or one per matched exercise on
   `(user_id, exercise_id, performed_at DESC, id DESC)`, that stops after `limit + 1` rows. A page at depth 49k
   costs the same as page 1. Filtered pages read ≤ 21 rows per matched exercise, even for the exercise last
   logged two years ago (the M5 skew case) and for the broad term `e` (51 × 12 rows).
2. **Records scale with the sets of one (user, exercise), not with the user's total.**
   - Each metric is an Index Only Scan with 0 heap fetches over the user + exercise slice of
     `workout_sets_pr_covering_idx` (D10), followed by a top-N sort.
   - A typical exercise with ~6k sets: 3.8 ms. The most-logged exercise of a 50k-entry user (53k sets):
     ~30 ms per request, using parallel workers.
   - A range query (one month) reads only that month: < 1 ms.
3. **Known limit: one exercise logged 50k times.** `perf-single` takes 80 ms p95: three scans of 213k index
   tuples, and up to 6 parallel worker processes on 2 vCPUs. This is the case D10 accepted. The scale path is a
   per-(user, exercise) record summary maintained in the POST transaction (D6), which makes all-time records O(1).
   Ranges and compare keep using this index; they stay ≤ 12 ms here.
4. **Ties on the top value cost one extra statement.**
   - The candidate query reads 50 rows. Only when all 50 tie does a second query fetch every tied set, and
     `findSets` loads them for exact ranking. That second query has no LIMIT (`personal-records.repository.ts`).
   - Measured: 174 plateau ties take 7.4 ms p95, and 53 natural ties 7.1 ms p95.
   - The cost grows with the number of identical sets. The review spike measured 66,668 identical sets at
     ≈ 0.5 s. That needs tens of thousands of sets at exactly one weight, so it is documented rather than bounded.
     Bounding it (`ORDER BY reps DESC, performed_at, id LIMIT n` on the tied value) is the fix if it ever matters.
5. **No row misestimate makes a plan worse, so no extended statistics (T1, decision D13).**
   - The estimate for `user_id = ? AND exercise_id = ?` is within 2.3× (e.g. 39,476 estimated vs 17,712 actual
     per worker).
   - The large ratios in the summaries are not misestimates. History's 49,256 estimated vs 21 actual is a LIMIT
     stopping early. The tie query's 1 estimated vs 174 actual still runs as an Index Only Scan.
   - `CREATE STATISTICS` did not change the one plan that looked suspicious in the review spike (a Seq Scan
     whose estimate was accurate).
6. **Concurrency is bounded by the connection pool.**
   - The pool is not configured, so it uses pg's default of 10 connections. A records request runs its three
     candidate queries in parallel, so 20 PR requests in flight compete for 10 connections: p95 153 ms (p50 114).
     20 history requests in flight: p95 80 ms.
   - Nothing fails, requests queue. With 2 vCPUs the database is also CPU-bound.
   - At scale: a configurable pool size, PgBouncer in transaction mode, and read replicas for history and records.
7. **Writes.** One entry: p95 4.2 ms. The max bulk (5,000 sets): p95 336 ms, of which ≈ 86 ms is in Postgres
   (two `createMany` statements, FK checks included). The rest is validation, metrics computed with decimal.js,
   and the 356 KB response.
8. **Index usage** during the plans pass matches the design. Every big-table index was used. Two indexes were
   not used, both expected:
   - `idempotency_keys_created_at_idx` (no idempotency keys in these scenarios; it exists for a future cleanup
     job, T2).
   - The trigram GIN index on the 150-row catalog. A Seq Scan is cheaper at that size; the index matters if the
     catalog grows (T3).
9. **Write amplification is the price of D10.** The PR covering index (177 MB) is larger than the
   `workout_sets` heap (139 MB). Each logged set writes three index entries on that table.

## 6. What would change at scale

| Pressure | Change |
|----------|--------|
| All-time records for exercises with very many sets (finding 3) | `exercise_records` summary per (user, exercise, metric), updated in the POST transaction; ranges stay on the covering index |
| Many concurrent coaches (finding 6) | Pool size from config, PgBouncer, read replicas for GET endpoints, a statement timeout |
| `workout_sets` growth (hundreds of millions of rows) | Partition by `user_id` hash, or by time with partition pruning on `performed_at` |
| Very large tie groups (finding 4) | Bound the tie query |
| Bulk POST latency | Already one transaction with two statements; the next step is COPY, or returning only ids instead of the full echo |
